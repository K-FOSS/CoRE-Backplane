# CoRE-Backplane Network/NATPuncher Stack

NATPuncher deploys CoTURN for STUN/TURN connectivity and runs a scheduled UPnP
mapping job where enabled. It is part of the [Network stack](../README.md) and
is owned by the [NATPuncher ApplicationSet](../../Apps/Network/NATPuncher.yaml).

The ApplicationSet injects the site-specific settings. Chart defaults are in
[`values.yaml`](values.yaml), and workload resources are rendered by
[`templates/common.yaml`](templates/common.yaml).

## CoTURN service configuration

The chart exposes the CoTURN Service settings under `coturn.service`:

```yaml
coturn:
  enabled: true
  service:
    type: 'LoadBalancer'
    loadBalancerClass: ''
    annotations: {}
    labels:
      wan-mode: 'public'
```

The [NATPuncher ApplicationSet](../../Apps/Network/NATPuncher.yaml) overrides
these generic defaults with the YXL PureLB class, public address, DNS names,
and dashboard labels. Keep site-specific load-balancer annotations and labels
in that ApplicationSet rather than in the chart defaults. `loadBalancerClass`
selects the Kubernetes load-balancer implementation; leave it empty when the
cluster's default implementation should be used. See the Kubernetes
[Service documentation](https://kubernetes.io/docs/concepts/services-networking/service/)
for the supported Service fields.

CoTURN's `portRange.min` and `portRange.max` are inclusive. YVR currently uses
the 50-port relay range `15000–15049`; the ApplicationSet also publishes that
range through UPnP for the configured target and both TCP and UDP protocols.
The YVR LiveKit kube-vip address `10.0.0.43` is also published through UPnP
for TCP `7881` and UDP `7882`, matching the live LiveKit media Service.
The YVR CoTURN kube-vip address `10.0.0.46` is published for both TCP and UDP
`3478`, matching the live CoTURN Service.
DC1 leaves `portRange` unset and uses the chart default of `15000–16000`.

## UPnP mappings

When `UPNP.enabled` is true, the `upnp` controller runs a Kubernetes CronJob
every 30 minutes. It uses `upnpc` from the
[`kristianfjones/upnp:jobs` image](https://hub.docker.com/r/kristianfjones/upnp)
to list existing IGD mappings and submit each entry in `UPNP.ports` with its
interface, target, ports, protocol and lease duration. Existing single-port
entries use `internalPort` and `externalPort`. A range entry uses inclusive
`internal.start`/`internal.end` and `external.start`/`external.end` fields:

```yaml
UPNP:
  ports:
    - target: '10.0.0.42'
      internal:
        start: 5000
        end: 5050
      external:
        start: 5000
        end: 5000
      protocol: TCP
      duration: 8600
```

The example maps matching internal and external ports from 5000 through 5050;
an external range with one port is treated as the base of a same-length mapping
range. For a translated range, provide equally sized internal and external
ranges. The job requests or renews router mappings; it does not configure
Kubernetes Services or prove that the router accepted the mappings or forwards
traffic externally.

The source and build documentation are in the publicly accessible DC1 Forgejo
[`CoRE/Core-Docker` repository](https://forge.core-dc1-talos-prod.dc1.yxl.writemy.codes/CoRE/Core-Docker).
Follow its UPNP image instructions for the Docker context, dependencies, build
arguments, tags and publishing. This chart currently uses
`kristianfjones/upnp:jobs` without an image digest or a build workflow in this
repository. Verify the published image and source revision in Forgejo before
releasing a replacement. Forgejo is publicly accessible, while account
registration is restricted.

The [fleet ApplicationSet](../../Apps/Network/NATPuncher.yaml) currently
disables UPnP on `core-dc1-talos-prod` and enables it on
`core-home1-talos-prod`. It injects the active port list and SR-IOV interface;
the values in [`values.yaml`](values.yaml) are chart fallbacks, not the
authoritative site configuration.

For the enabled site, verify the interface can reach the router at Layer 2,
the SR-IOV resource is available, and router policy permits the mappings.
Inspect CronJob and Job events and logs, then test each mapping from outside
the routed network. When updating the image, record its source revision, build
inputs, immutable digest and runtime compatibility in the Forgejo build docs,
then pin the deployment to that artifact. Keep the chart command and `upnpc`
flags compatible with the image.

## CoTURN

CoTURN provides STUN/TURN and uses REST/shared-secret authentication. The
`natpuncher-turn-auth` Secret is generated by External Secrets and injected at
startup; its value is not stored in Git or the ConfigMap. TURN clients derive
time-limited credentials using CoTURN's
[REST API authentication format](https://github.com/coturn/coturn/blob/master/README.turnserver).

CoTURN connects to the site-local Dragonfly Service ClusterIP and uses the
public Dragonfly hostname as TLS SNI. Update `dragonflyAddress` in the
[ApplicationSet](../../Apps/Network/NATPuncher.yaml) if that Service is
recreated with a different ClusterIP.

The generated `natpuncher-turn-auth` Secret is published to CoreVault using
the [External Secrets Operator PushSecret](https://external-secrets.io/latest/api/pushsecret/)
at `Network/NATPuncher/<region>/<datacenter>/<cluster>/TurnAuth`, under
`Password`. Consumers on other clusters should read that path through an
ExternalSecret. Do not copy the Kubernetes Secret or store its value in Git.

Validate STUN discovery and authenticated TURN allocations from outside the
cluster. Test UDP and TCP/TLS separately, and monitor allocation failures,
bandwidth, port exhaustion and authentication errors.

Do not enable anonymous relay, expose management interfaces, or use weak static
credentials.
